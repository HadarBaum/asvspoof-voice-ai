# 10-minute presentation script

Hebrew version: `docs/PRESENTATION_SCRIPT.he.md`.

## How to use this document

It has two layers, and mixing them up will overrun your slot:

- **SAY** blocks (`>` quoted) are the words you actually speak. They total **1,635
  words — about 11.3 minutes** at 145 wpm, so there is over a minute to trim. In
  order of what I would cut first: the confidence-histogram paragraph in the
  streamed-eval section, the second half of trade-off **four** in the closing, and
  the ROC sentence on the dev-results slide (the chart speaks for itself). All
  three are covered in the DEEPER blocks for Q&A. Cutting those lands you at ~10:00.
- **DEEPER** blocks are everything behind each slide, in full. They are **not**
  meant to be read aloud — they exist so you can answer any follow-up without
  hunting through `EXPLANATION.md` mid-Q&A. Speaking the whole document would
  take about 25 minutes.

Then three reference sections at the end: a **feature glossary** (what MFCC,
energy, rolloff and the rest actually mean), the **complete trade-off register**
(every deliberate choice in the project, including all five bullets on the
Challenges slide), and **anticipated questions**.

Every figure comes from `docs/training_metrics.json`, `docs/model_comparison.json`
and the 2,000-utterance run in `docs/RESULTS.md`. Re-check them if you re-run the
pipeline before presenting.

**Time budget.** The demo is the only section with real slack. If you are behind
when you reach it, cut the similar-clips playback — never the threshold story.

## 0:00 — 0:45 · Problem & dataset

> Can you tell whether a voice you just heard was a real person, or generated by
> an AI? That's the question this project answers, end to end, on real data.
>
> We use ASVspoof2019 — an anti-spoofing benchmark for speaker verification. It
> ships two partitions, and choosing between them was our first real decision.
> LA, Logical Access, is genuine human speech versus speech synthesized by
> nineteen different text-to-speech and voice-conversion systems. PA, Physical
> Access, is a human recording replayed through a loudspeaker.
>
> We use **only LA**, deliberately. "Human or AI" only means something against
> synthetic audio. PA's attacks are a real human voice played back — labelling
> that "AI" would have been a false claim, so we left it out rather than inflate
> our dataset size.
>
> Twenty-five thousand training clips, twenty-five thousand dev clips, and the
> partitions are speaker-disjoint — which matters later.

**DEEPER.** Each partition ships a `flac/` folder of 16 kHz mono clips and a
protocol `.txt` with one line per clip: `<speaker_id> <file_id> - <attack_id>
<bonafide|spoof>`, where `attack_id` is `-` for bonafide. Attacks are labelled
A01–A19; train/dev carry A01–A06, eval carries A07–A19 — so **the eval attacks
are systems the model never saw in training**. That is the point of the benchmark
and it explains why eval numbers sit below dev numbers: it is measuring
generalization to unseen synthesis methods, not memorization.

Excluding PA cost us half the available data. The alternative was worse: PA
mislabels "a human recording played back" as AI, which is a different and false
claim. We would rather defend a smaller honest scope.

## 0:45 — 1:30 · Architecture + Architecture diagram

> [Advance through both architecture slides together.]
>
> Five course technologies, each doing real work. MinIO is the object store
> holding raw audio. Spark does the heavy batch feature extraction.
> Elasticsearch is the NoSQL store for features, embeddings and predictions.
> Kafka is the streaming backbone. Docker Compose runs the three services.
>
> The one rule that shapes this whole diagram: **feature extraction and the model
> exist in exactly one place each.** `common/features.py`, and one saved model
> artifact. The Spark batch job, the Kafka consumer and the web app all import
> those same two things. That's what makes this one AI capability applied three
> ways, instead of three separate features that could silently drift apart.

**DEEPER.** The three containers are MinIO (`9000` S3 API, `9001` console), Kafka
on `9092` in **KRaft mode** — no ZooKeeper container, which is the modern way to
run it — and single-node Elasticsearch on `9200` with security disabled.
Ports are published to the host because the pipeline scripts run on the host, not
in containers.

Spark runs on the host too, via `pip install pyspark` in local mode, not in a
container. Getting a containerized Spark driver to reliably reach host-exposed
Kafka/MinIO/Elasticsearch ports on Windows is real work with no payoff at this
scale. Security disabled and single-node are appropriate for a local course
project and would both be wrong in production — say that plainly if asked.

The "one place each" rule is enforced by `common/model.py`. Before it existed,
`streaming_enrichment.py` and `app/server.py` each hardcoded `>= 0.5` as the
cutoff. Centralizing the model *and its threshold* into one artifact is what made
the threshold fix take effect everywhere at once instead of needing to be
remembered at every call site.

## 1:30 — 3:00 · Ingest → Transform → Feature vector → Load

> [Four slides. Keep moving — roughly 22 seconds each.]
>
> Ingest: we parse the dataset's own protocol files and upload every clip to
> MinIO. We talk to it with plain `boto3` — MinIO speaks the S3 API, so this is
> literally the same client code that would talk to AWS.
>
> Transform is the actual big-data step. A Spark RDD of about fifty thousand
> clips, repartitioned so work spreads across cores. The detail that matters is
> `mapPartitions` rather than `map` — it runs once per Spark task instead of once
> per row, so we build one MinIO client per task instead of fifty thousand.
>
> [Feature-vector slide.]
>
> Each clip becomes exactly 53 numbers. Forty of them are MFCCs — twenty
> coefficients, each as a mean and a standard deviation. MFCCs describe the shape
> of the vocal tract, essentially voice quality, or timbre. Then six numbers for
> spectral shape — brightness, spread, and where the high end rolls off. Four for
> noisiness and loudness. Two for pitch. And clip length.
>
> We take the mean and standard deviation of frame-level features rather than the
> raw frames, so every clip maps to the same 53 columns no matter how long it is.
>
> The intuition to hold onto is in the standard deviations. Real speech is
> physically messy — articulators move, pitch wobbles. Synthesis tends to be too
> smooth, too regular. And that is exactly what our model keyed on.
>
> Load: the feature table goes to Parquet, and the same rows get bulk-indexed
> into Elasticsearch.

**DEEPER — see the Feature glossary below for what each group means physically.**

On the Spark write path: the feature table is written with `pandas`/`pyarrow`, not
Spark's own `DataFrameWriter.parquet()`. Spark's native writer needs
`winutils.exe` on Windows — it shells out to Hadoop's local filesystem code to set
POSIX permissions, and fails with `HADOOP_HOME and hadoop.home.dir are unset`
without that binary. Rather than install a third-party native binary to satisfy a
permissions call, we `toPandas()` the (small — one row per utterance, not per
audio sample) result and write it with pandas. **Spark still does the distributed
work**; only the final write changed.

On reading from MinIO inside `mapPartitions` rather than via an S3A connector:
S3A needs specific Hadoop jars whose versions must match the Spark/Hadoop build
exactly, a notorious source of version-mismatch failures. Plain `boto3` inside an
RDD transformation sidesteps it entirely — executors just run ordinary Python. The
cost is that Spark doesn't know these are S3 reads and can't plan around them,
which is irrelevant here because there is no I/O-aware planning we'd benefit from.

Load writes to two places in one pass: Parquet (what `train_classifier.py` and
`index_embeddings.py` read) and the `asvspoof-training-features` index (50,224
docs) so aggregations can run without touching Parquet. `foreachPartition` again
builds one Elasticsearch client per partition, not per row.

## 3:00 — 4:00 · Classification + How EER is calculated

> We didn't commit to one model. We trained two on identical features — Random
> Forest and Gradient Boosting — and let a metric choose between them.
>
> We split by the dataset's own train and dev columns, never randomly. A random
> split could put the same speaker on both sides, and then the model partly
> learns to recognize *that speaker* rather than what synthetic audio sounds
> like. Your dev score goes up and your real performance doesn't.
>
> [EER slide.]
>
> We selected on **Equal Error Rate** — the operating point where the false-accept
> rate and the false-reject rate are equal. Two reasons. It's
> threshold-independent, so you can't flatter it by moving a cutoff. And it's the
> metric the official ASVspoof challenge itself is scored on.
>
> Gradient Boosting won: EER 9.3% against Random Forest's 12.3%, ROC-AUC 0.970
> against 0.951.

**DEEPER.** Both models are reweighted for the train set's imbalance —
`class_weight` for Random Forest, `compute_sample_weight("balanced", ...)` for
Gradient Boosting, which has no `class_weight` parameter. The winner's model, its
name, and its EER-optimal threshold are bundled into a single `joblib` artifact.

`compute_eer()` sweeps thresholds, tracks false-acceptance against
false-rejection, and returns both the error rate *and the score threshold at the
crossing point* — that threshold is what gets stored and used instead of 0.5.

Why two tree ensembles and not a CNN over spectrograms: a CNN would likely score
higher, but feature importances stay directly inspectable on tree ensembles, and
we can read sklearn's source and defend every line. We traded a few points of
score for being able to explain the model completely. That is a deliberate choice
against the course brief's emphasis on understanding over complexity — say so
directly if challenged, don't pretend it was a performance decision.

Why compare two models at all rather than pick one: an unchallenged single number
is weaker evidence than a real comparison, and training is fast enough on a laptop
that the comparison is nearly free. Full numbers in `docs/model_comparison.json`.

## 4:00 — 5:30 · Results on dev — the accuracy paradox, found and fixed

> [Slow down. This is the most important slide in the deck.]
>
> This is where the project got interesting, and it's the part I would most want
> to be asked about.
>
> Our first version reported 92.3% dev accuracy. That sounds like a finished
> project. Then we looked at the per-class breakdown. It caught 99.8% of spoofed
> audio — and only **28%** of real human speech.
>
> The reason is that dev is about 90% spoof. A model that simply leans toward
> "spoof" scores beautifully on accuracy while being nearly useless at the job we
> actually care about. Accuracy was hiding the failure, not measuring it.
>
> Two separate fixes, and it matters which is which. **Switching models** took
> bonafide recall from 28% to 80% with no threshold change at all — Gradient
> Boosting's probabilities are simply far less skewed. **Then switching the
> threshold**, from scikit-learn's default 0.5 to the EER-optimal 0.689, took it
> from 80% to **90.7%**.
>
> And the honest part: overall dev accuracy went *down* when we did that — 94.3%
> to 90.7%. Bonafide precision dropped too, from 0.93 to 0.53. We now call more
> things human, including some spoofs we used to catch. That is a real trade. You
> cannot maximize both classes at once on imbalanced data; you can only choose
> where on the ROC curve to sit. We chose the principled point over the default.

**DEEPER.** The original Random Forest report, for reference:

```
                  precision    recall  f1-score   support
bonafide (human)       0.93      0.28      0.42      2548
      spoof (AI)       0.92      1.00      0.96     22296
```

And the deployed Gradient Boosting model at its EER threshold:

```
                  precision    recall  f1-score   support
bonafide (human)       0.53      0.91      0.67      2548
      spoof (AI)       0.99      0.91      0.95     22296
```

**Be careful with the headline.** "28% → 91%" is fair for "the original naive
approach versus the final deployed one," but it is the combined effect of two
changes. The 28% is Random Forest at 0.5; the 91% is Gradient Boosting at its EER
threshold. Gradient Boosting's *own* default-threshold number is 80.2%, not 28%.
The dashboard and slides show Gradient Boosting only, so their "before" column is
80.2%. Conflating these is a mistake this project already made once and corrected
(commit `8db0c48`) — don't reintroduce it under questioning.

Why reweighting wasn't enough on its own: `class_weight`/`sample_weight` reweight
the *training loss*. The default 0.5 threshold applied at *evaluation* time is a
separate lever. Fixing one does not fix the other — that is the actual technical
lesson of this slide.

| Bonafide recall @ 0.5 | 28.0% | 80.2% |
| Bonafide recall @ own EER threshold | 88.1% | 90.7% |

## 6:00 — 6:30 · AI capability 2 — embeddings & semantic search

> Second capability: the same feature vectors reused as an embedding. No second
> model, no pretrained audio encoder.
>
> One step is necessary to make that work. Raw features live on wildly different
> scales — duration in seconds against rolloff in the thousands — so unscaled
> cosine similarity would just be dominated by whichever column has the biggest
> magnitude. We standardize, store the scaler so the web app treats a fresh
> upload identically, and write the vectors into a `dense_vector` field on the
> index that already existed.
>
> Then every classification runs a k-nearest-neighbour search for the five most
> acoustically similar training clips.

**DEEPER.** `k=5`, `num_candidates=100`, cosine similarity. The field was added to
the existing `asvspoof-training-features` mapping in place via `put_mapping` —
that index already held 50,224 expensively-computed documents, and Elasticsearch
allows adding a new field to an existing mapping as long as there's no type
conflict. So: no reindex, no reprocessing, no re-running Spark. The bulk request
uses `_op_type: update` because the raw feature columns don't need to change.

Reusing the classifier's features as the embedding is a **trade-off, not just a
shortcut** (it is bullet 3 on the Challenges slide). A pretrained speaker-embedding
model would almost certainly retrieve better neighbours. But it would add a second
model, a second dependency, and a second thing to explain — and it would break the
"one feature extractor" property that makes the whole project defensible. We chose
self-containment.

`index_embeddings.py` reads the same Parquet table as training and doesn't depend
on the trained model at all, so it can run before, after, or independently of
`train_classifier.py`.

## 6:30 — 7:00 · AI capability 3 — streaming enrichment

> Third application. Kafka replays eval clips as events — metadata only, the
> MinIO key and the true label, not the audio. A consumer fetches each clip from
> MinIO, extracts the same 53 features, scores it with the same model, and writes
> an enriched prediction into Elasticsearch: one document per clip, as it
> arrives, not batched afterwards.
>
> This is the part that independently confirmed the threshold fix. And everything
> on the next three slides is scored right here — on the eval partition, attacks
> A07 through A19, synthesis systems the model never saw during training.

**DEEPER.** The consumer joins a named group (`--group-id`) with auto-commit, so
Kafka tracks read position. Without a group id every run restarts from the
earliest offset and re-scores everything — which happened during early testing: a
run scored 20 utterances, and re-running scored the same 20 again.

That same mechanism is why switching models required a **new** group id
(`asvspoof-streaming-enrichment-gb`). Reusing the old one would have resumed from
its committed offset and scored only the remaining messages with the new model,
mixing old-model and new-model predictions in one comparison. A fresh group name
re-reads from the beginning.

Why a plain Python consumer rather than Spark Structured Streaming: per-message
scoring is light. Routing it through Spark would mean pulling the
`spark-sql-kafka-0-10` connector in via Maven at runtime for a workload with no
need of distributed execution. Kafka is still doing real work as the event
backbone; Spark earns its place in the batch stage instead.

MinIO keys contain slashes, and Flask's default `<string:...>` stops matching at
the first one. The similarity search is wrapped in its own try/except so it can
never block the main classification result — it's a bonus, not the answer.

## Feature glossary — what the 53 numbers actually mean

Use this for any "what is an MFCC?" question. Physical meaning first, then why it
helps detect synthesis.

### MFCCs — 20 coefficients × mean and std = 40 numbers

**Mel-Frequency Cepstral Coefficients.** How they're computed, in five steps:

1. Cut the audio into short overlapping frames (tens of milliseconds).
2. Take the spectrum of each frame — how much energy at each frequency.
3. Sum that energy into a **mel filterbank**. The mel scale spaces filters by
   *perceived* pitch rather than raw Hertz, so there is fine resolution at low
   frequencies where human hearing discriminates well, and coarse resolution up
   high where it doesn't.
4. Take the **logarithm** of each filter's energy — roughly how loudness is
   perceived, and it turns the multiplication of "voice source × vocal tract
   filter" into an addition, which separates them.
5. Apply a **discrete cosine transform**, which decorrelates the filter energies
   and compacts the information. Keep the first 20 coefficients.

What you get is a compact description of the **spectral envelope** — the smooth
overall shape of the spectrum, as opposed to its fine detail. Physically that
envelope is set by the shape of the vocal tract: tongue, jaw, lips. Perceptually
it is **timbre**, or voice quality — the thing that makes two people singing the
same note sound different. Low coefficients capture the broad shape; higher ones
capture finer ripples in it.

**Why it detects synthesis:** TTS and voice-conversion systems reconstruct that
envelope through a vocoder, and do it imperfectly. The errors are subtle and
usually inaudible, but they show up in the statistics — especially in how the
envelope *changes over time*.

### Spectral shape — 6 numbers

- **Spectral centroid** (mean, std) — the energy-weighted average frequency. The
  "centre of mass" of the spectrum. Perceptually, **brightness**.
- **Spectral bandwidth** (mean, std) — how widely energy is spread around that
  centroid. Narrow means concentrated and tonal; wide means diffuse.
- **Spectral rolloff** (mean, std) — the frequency below which most of the energy
  (librosa's default is 85%) lies. Effectively **where the high end dies off**.
  This one is a good synthesis detector because vocoders frequently band-limit or
  over-smooth the top of the spectrum.

`spectral_bandwidth_mean` is the third most important feature in our model, at
7.5%.

### Signal level — 4 numbers

- **Zero-crossing rate** (mean, std) — how often the waveform crosses zero per
  frame. A cheap proxy for **noisiness / high-frequency content**. It is high in
  fricatives like /s/ and /ʃ/, low in voiced vowels. Fricatives are a classic
  weak point for synthesis, because they are noise rather than tone.
- **RMS energy** (mean, std) — root-mean-square amplitude per frame, i.e.
  **loudness**. The mean is overall level; the std is dynamic range. Synthetic
  speech often has flatter dynamics than a real speaker.

### Pitch — 2 numbers

**Fundamental frequency (F0)**, mean and std — the rate the vocal folds vibrate,
which is what you hear as pitch. Extracted with `librosa.yin` over 50–500 Hz,
covering a deep bass to a high soprano or child.

`pitch_std` is the interesting one: it measures **vibrato and jitter**. Human
pitch is never perfectly steady — it drifts and wobbles constantly. Many TTS and
VC systems produce unnaturally stable pitch. This is the most intuitive feature to
explain to a non-technical audience.

*Implementation note, in case you're asked why `yin` and not `pyin`:* `pyin` adds
probabilistic HMM smoothing over a 4+ octave range and measured 2–9 seconds per
clip — at 50,000 clips, many hours. Plain `yin` over a voice-only range with a
larger hop gets comparable signal in ~0.02 s. That is a ~100× speedup for a
summary statistic that doesn't need frame-level precision.

### Duration — 1 number

Clip length in seconds.

### Why mean and std, and what it costs

Averaging frame-level features gives every clip the same 53 columns regardless of
length, which is what a tabular classifier requires.

**The cost is real and worth naming:** mean/std pooling throws away *temporal
order*. The model sees the distribution of what happened, never the sequence. It
cannot notice that a particular artifact occurs at a word boundary, or that pitch
rose and then fell. A sequence model — an RNN, or a CNN over the spectrogram —
would capture that and would very likely score better. This is the same trade as
choosing tree ensembles: we gave up modelling power for a fixed-shape input and a
model we can fully explain.

## Complete trade-off register

Every deliberate choice, with what it cost. The five marked **[SLIDE]** are the
bullets on the Challenges slide.

| # | Choice | What we gave up |
|---|---|---|
| 1 | LA partition only, not PA | Half the available data — but PA would mislabel replayed human speech as "AI" |
| 2 | Mean/std pooling, not raw frames | All temporal ordering; a sequence model would likely score better |
| 3 | `librosa.yin`, not `pyin` | HMM-smoothed pitch precision, for a ~100× speedup across 50k clips |
| 4 | Two tree ensembles, not a CNN | Probably a few points of score, for fully inspectable feature importances |
| 5 | Dataset's own split, not random **[SLIDE]** | Apparent accuracy — a random split leaks speakers and inflates dev scores |
| 6 | EER threshold, not 0.5 **[SLIDE]** | Spoof recall and bonafide precision (0.93 → 0.53), to take bonafide recall 80% → 91% |
| 7 | Own features as embedding, not a pretrained encoder **[SLIDE]** | Retrieval quality, to keep semantic search self-contained and explainable |
| 8 | Python end to end, not Scala **[SLIDE]** | Spark's native language — but the feature library is Python-only, and two implementations could disagree |
| 9 | Spark-on-Windows friction, diagnosed **[SLIDE]** | Time — worker Python resolution, path-with-spaces, a pyspark/Python-3.12 incompatibility, and a removed `distutils` |
| 10 | `boto3` in `mapPartitions`, not S3A | Spark's I/O-aware planning (which we'd gain nothing from), to avoid Hadoop jar version hell |
| 11 | `pandas.to_parquet`, not Spark's writer | Nothing functional — avoids needing `winutils.exe` for a permissions call |

| 17 | ES single-node, security off | Production-realism, appropriate for a local project |

## Anticipated questions

**"What is an MFCC, in one sentence?"** A compact description of the shape of the
vocal tract — voice quality, or timbre — computed by taking the spectrum, warping
it to the perceptual mel scale, taking logs, and decorrelating with a cosine
transform.

**"Why is A17 so bad?"** A17 is a waveform-filtering voice-conversion attack whose
scores sit closest to the bonafide range, and it is known as the hardest attack in
LA. Our EER threshold buys bonafide recall by giving up margin exactly there. It is
the visible cost of trade-off #6.

**"84.8% seems low."** Raw accuracy is the wrong metric on a set that is 88%
spoof — a trivial always-spoof baseline beats it. Balanced accuracy is 89.3% and
dev EER is 9.3%. Get in front of this rather than defending 84.8%.

**"Would a neural network do better?"** Almost certainly on score. We chose tree
ensembles so feature importances stay inspectable and we can explain every line.
A deliberate trade of points for defensibility.

**"Is 2,000 clips enough?"** For the headline, yes — it barely moved from the
498-clip run (84.9% → 84.8%), so the estimate is stable. The per-attack bars are
the loose ones, at roughly ±6 to ±9 points.

**"Why didn't you stream all 5,000?"** Consumer throughput collapsed under
sustained load for reasons we never conclusively identified. More clips would
tighten the per-attack intervals but not change the headline — the 4× jump from
498 to 2,000 moved it by 0.1 points.

**"Could this be fooled by a new TTS system?"** Almost certainly, and our own
eval set demonstrates the principle: eval attacks A07–A19 are systems absent from
training, and the three we handle worst are the ones acoustically closest to real
speech. Generalization to unseen synthesis is the open problem in this field, not
a solved one.
